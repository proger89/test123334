# Виртуальная смена ВСМ
## Техническое задание для реализации

**Версия 4.0 · 25 сентября 2026 года**  
Команда «НаракаТОПчик»  
Сдать решение: **27 сентября, 23:59 МСК**. [1, с. 6]

### Что собираем

Браузерную обучающую игру для проводников. Игрок разбирается с обращениями пассажиров, выбирает действия, следит за временем и видит последствия. После смены он получает разбор, очки, достижения и предложение следующей тренировки.

**В сдаваемой версии работают все девять функциональных требований.** Профиль, рейтинг, уведомления и аналитика — не картинки и не разделы «в разработке».

**Оформление берём с выбранного пользователем листа.** Сохраняем полуреалистичных персонажей, светлые панели, тёмно-синие заголовки и синие кнопки. Предыдущий упрощённый векторный набор не подменяет этот образец.

![Выбранный образец оформления](graphics/reference/board.png)

### С чего начать сегодня

Сначала договориться о структуре состояния игры и правилах двух сценариев. Затем сделать один полный проход через сервер: начало → выбор → сохранение → разбор. После этого подключать красивую сцену и остальные разделы в порядке из раздела 20.

**Граница документа.** Требования организатора обозначены ссылкой [1]. Содержание ситуаций — ссылкой [2]. Экраны, названия файлов, игровые секунды, баллы и порядок разработки ниже — предложенные решения команды, а не утверждённые нормативы перевозчика. Их можно реализовать сейчас, а спорные предметные правила сверить с экспертом.

### Что ещё обязательно

Раздельные интерфейс и серверная часть, база данных, описанный программный интерфейс — API, инструкция локального запуска, история изменений в Git и отсутствие реальных персональных данных и ключей в материалах сдачи. [1, с. 1–3, 5–6]

### Что не входит в первую сдачу

Свободная ходьба по трёхмерному вагону, голосовое управление, свободный разговор с нейросетью, промышленное подключение к кадровым системам, магазин наград, большой кабинет руководителя и графический редактор сценариев. Для изменения сценариев достаточно файлов с данными и команды проверки.

Сокращаем число сценариев и декоративных деталей, но не вычёркиваем девять требований. В оценке допускается небольшое число содержательных сценариев; декоративные таймеры и шкалы, напротив, снижают оценку. [1, с. 4]

# 2. Профиль и навигация

## Требование 1. Управление профилем

При первом входе человек нажимает «Создать учебный профиль». Сервер создаёт аккаунт и назначает вымышленное имя, например «Проводник-742». Разрешено изменить псевдоним и выбрать портрет. Не запрашивать паспорт, телефон, настоящее имя, сведения о работе или почту.

Профиль содержит: идентификатор, псевдоним, портрет, учебную бригаду и депо, основные очки компетенций, действующие временные баллы, уровень, количество завершённых сценариев, достижения и историю попыток. Выбор учебной группы не даёт административных прав.

Аккаунт сохраняется на сервере. Браузер получает защищённую сессию. После обновления страницы человек остаётся в своём профиле. Для первой версии восстановление после удаления данных браузера не предусмотрено — это явно написано на экране входа и в ограничениях.

### Основные экраны

| Экран | Содержимое и действия |
|---|---|
| Профиль | Очки, уровень, достижения, история, «Продолжить смену», «Выбрать сценарий». |
| Сценарии | Название, чему учит, режим, состояние прохождения, «Начать». |
| Смена | Сцена вагона, обращения, портрет говорящего, текст, действия, сроки и две шкалы. |
| Результат | Итог, полученные очки, достижения, подробный разбор и повторная попытка. |
| Прогресс | Компетенции, число наблюдений, ошибки, изменение результатов, рекомендации. |
| Рейтинг | Три масштаба сравнения: бригада, депо, компания. |
| Уведомления | Три типа сообщений, отметка прочтения, переход к связанному материалу. |

В верхней панели всегда доступны профиль, сценарии, прогресс, рейтинг и уведомления. Достижения можно открыть внутри профиля: отдельная большая страница не нужна.

### Проверка готовности

Создать новый профиль, пройти сценарий, обновить страницу. Псевдоним, история и заработанные очки сохранились. Другой браузер создаёт другой профиль и не получает доступ к первой попытке. Пустая история выглядит как приглашение начать обучение, а не как ошибка.

Для рейтинга заранее создать вымышленные учебные записи и пометить их в интерфейсе. Не представлять эти записи как результаты реальных сотрудников.

# 3. Как работает сценарий

## Требование 2. Движок сценариев

Сценарий хранится в отдельном файле JSON. Это описание ситуаций и переходов, а не программа внутри текста. Код умеет читать одинаковую структуру для обоих сценариев. Добавление реплики, условия или достижения не требует переписывания движка.

В каждом сценарии есть идентификатор, версия, название, исходные условия, начальные шкалы, действующие обращения, узлы диалога, варианты действий, сроки, правила оценки, исходы и ссылки на источники.

### Что хранится в узле

| Поле | Смысл |
|---|---|
| `id`, `speaker`, `text` | Какой это шаг, кто говорит, что видит игрок. |
| `actions` | Доступные решения. У каждого свой идентификатор и текст. |
| `conditions` | Когда решение разрешено: например, владелец вещи уже установлен. |
| `effects` | Изменение признаков, шкал, состояния предмета или другого обращения. |
| `next` | Следующий шаг текущего обращения. |
| `deadline`, `on_timeout` | Срок и отдельное последствие пропуска. |
| `explanation`, `source_ref` | Объяснение для разбора и конкретный исходный материал. |

Сервер отдаёт браузеру только текущее состояние и доступные действия. Будущие правильные ответы, закрытые ветки и полную таблицу баллов до конца попытки не передавать.

### Два обращения одновременно

В первой смене есть обращение об оборудовании и обращение о багаже. У каждого собственный текущий шаг. Выбор другого обращения меняет фокус интерфейса, но не сбрасывает чужое состояние и не останавливает его срок.

Состояние попытки включает версию сценария, режим, шаги обоих обращений, признаки вроде `owner_known`, две шкалы, нарушения, сроки и порядковый номер изменения. Выбор игрока сохраняется сразу, а не только в конце.

### Проверка готовности

Один маршрут проходит через проверку места, другой сначала через передачу сообщения ответственным сотрудникам. Оба могут завершиться правильно. Нельзя предложить свободное место как подтверждённое до проверки. Несуществующий шаг или неизвестное правило не позволяет опубликовать сценарий.

В опубликованной версии ничего не менять задним числом. Новая правка создаёт новую версию; начатые и завершённые попытки остаются на своей.

# 4. Время и режимы прохождения

## Требование 3. Система таймеров

На экране показывать не произвольные бегущие цифры, а остаток до срока конкретного обращения. Возле числа писать, что требуется: например, «Освободить проход». Время задаётся в сценарии и проверяется сервером.

**Начальные учебные настройки:** в первой смене 45 секунд на освобождение прохода с момента появления второго обращения; во второй — 35 секунд на предусмотренное информирование. Это не нормативы из документов заказчика. До консультации с экспертом отображать отметку «Учебное ограничение времени».

### Два режима

| Режим | Как ведут себя время и результаты |
|---|---|
| Обучение | Есть подсказки, явная пауза и повтор. На паузе остаток времени сохраняется. Попытка не участвует в рейтинге. |
| Проверка | Нет подсказок и паузы. Закрытие вкладки не останавливает срок. Только завершённая зачтённая попытка даёт основные очки. |

Перед началом проверки написать это обычным текстом и получить подтверждение игрока. Загрузка изображений сама по себе не запускает критическое событие: сначала загружается экран, затем пользователь нажимает «Начать».

### Серверное поведение

В базе хранить точное время окончания срока. Отдельный постоянно работающий обработчик раз в секунду проверяет активные сроки. Браузер во время смены получает состояние примерно раз в секунду; ответы игрока проверяются немедленно. Даже при закрытом браузере просрочка будет записана обработчиком.

Если время сервера равно сроку или больше него, сначала срабатывает просрочка. После этого действие разрешается или отклоняется уже по новому состоянию. Отправленное ранее, но не принятое сервером действие не считать автоматически своевременным.

Обработчик просрочки и обработчик действий используют одну и ту же блокировку попытки. Просрочка применяется один раз. Часы компьютера игрока не влияют на оценку.

### Проверка готовности

Не нажимать кнопки до окончания срока; обновить страницу; закрыть вкладку и вернуться; нажать ровно на границе; поставить обучение на паузу. Во всех случаях время и последствия совпадают с выбранным режимом. При потере связи показать сообщение, а не бесконечно ждать ответа без объяснения.

# 5. Шкалы и начисление очков

## Требование 4. Двойная шкала оценки

«Лояльность пассажира» и «Рейтинг безопасности» — два отдельных значения от 0 до 100. Решение может улучшить одно и ухудшить другое. Возле изменения показывать короткую причину. Цвет дополняется названием и числом.

Во всех примерах ниже начальные значения: лояльность 60, безопасность 80. Все прибавления и вычитания ограничиваются диапазоном 0–100. **Числа, формула и пороги этого раздела — учебные настройки команды, не официальный стандарт.**

### Оценка попытки

Каждый сценарий содержит фиксированный список проверяемых действий. В первой смене их девять, во второй — четыре. У каждого действия один результат: выполнено или не выполнено. Повторение одного действия не увеличивает число выполненных пунктов.

`Оценка = округлить(100 × выполненные пункты / все пункты сценария)`

Условия зачёта: закончены обязательные обращения, нет критической ошибки, итоговая безопасность не ниже 80, оценка не ниже 70. При незавершённой попытке очки не начисляются. При незачёте разбор и оценка сохраняются, но зачётных очков нет.

Критическая ошибка — отдельная запись, а не просто штраф на шкале. Повышение лояльности или последующее улучшение безопасности не стирает её. В первой смене пропуск срока отмечается отдельно и снижает безопасность; во второй перемещение бесхозной вещи или пропуск предусмотренного информирования отмечается как критическая учебная ошибка. Классификацию подтвердить у эксперта.

### Основные и временные баллы

Основные очки компетенций: сумма лучших зачтённых оценок по двум сценариям в фиксированном наборе версий. Повторный результат 78 после 78 добавляет 0. Результат 89 после 78 добавляет 11. Понижение результата не отнимает основные очки.

Временные баллы: отдельные игровые награды за учебное испытание. Они имеют срок действия, показываются отдельно и действительно сгорают. Они не отменяют ошибки и не изменяют оценку конкретной попытки.

Уровень зависит только от основных очков: 1-й — 0–49; 2-й — 50–99; 3-й — 100–199; 4-й — от 200. Рейтинг сравнивает основные очки плюс ещё действующие временные баллы. Разложение суммы видно пользователю.

# 6. Достижения и рейтинг

## Требование 5. Система достижений

| Достижение | Условие выдачи |
|---|---|
| «Первая смена» | Впервые завершить любой сценарий в обучении или проверке. |
| «Верный приоритет» | Зачесть первую смену, освободив проход до срока. |
| «Внимание к обстоятельствам» | Зачесть второй сценарий без перемещения бесхозной вещи. |
| «Две ситуации — два решения» | Получить зачёт по обоим сценариям в режиме проверки. |

У каждого достижения постоянный идентификатор, название, описание, изображение и правило. В профиле видны дата получения и попытка-основание. Неполученные достижения показываются приглушённо, вместе с условием, а не как неработающие кнопки.

Проверка условий запускается после сохранения результата. Пара «профиль + достижение» уникальна в базе. Одновременное завершение или повтор сетевого запроса не создаёт две награды.

## Требование 6. Таблица лидеров

Переключатель «Моя бригада / Моё депо / Компания» меняет состав участников. Показывать место, псевдоним, уровень, основные очки, действующие временные баллы и итоговую сумму. Строка текущего игрока выделена.

Сортировка: сумма по убыванию; затем основные очки по убыванию; при полном равенстве — стабильный порядок по идентификатору. Равные значения получают одинаковое место. Не использовать скорость ответа как скрытый способ решить ничью.

Не начислять очки за обновление страницы, повтор просмотра разбора, показ анимации достижения или повтор уже отправленного запроса. Основные очки привязаны к конкретному набору версий сценариев; новый текст не должен автоматически создавать второй источник тех же очков.

### Проверка готовности

Игрок получает результат 78, затем 78, затем 89: его основные очки меняются на +78, +0, +11. После выдачи временной награды +20 сумма рейтинга увеличивается на 20. После истечения её срока сумма уменьшается на 20, основные очки и уровень не меняются.

Создать две учебные бригады в двух учебных депо и проверить фильтры. На каждой странице вымышленные начальные записи обозначены как демонстрационные.

# 7. Разбор решений

## Требование 7. Обратная связь

После завершения показывать итог: зачтено или нужна повторная тренировка, обе шкалы, выполненные пункты, полученные очки и новые достижения. Затем — последовательный разбор всех решений, включая бездействие, которое привело к просрочке.

### Карточка одного решения

| Часть | Что показывать |
|---|---|
| Обстоятельства | Какое обращение было активно и что игроку было известно. |
| Действие | Текст выбранного варианта или «Время истекло». |
| Последствия | Изменение ситуации и обеих шкал; нулевые изменения тоже допустимы. |
| Объяснение | Почему применено именно это правило. Не только «неверно». |
| Альтернатива | Какое доступное в тот момент действие помогло бы лучше. |
| Основание | Название материала, страница и номер ситуации; отдельно — учебные допущения. |

Например: «Вы продолжили обсуждать оборудование. К окончанию учебного срока проход оставался занят. Безопасность −25. В ситуации № 14 требуется установить владельца и предложить конкретное место для вещи. Сам срок 45 секунд задан авторами тренажёра».

Не писать, что источник требует именно такой балл или точное время, если этого там нет. Не давать ссылку на отсутствующий документ или выдуманный пункт.

### Повторение

Обязательная кнопка «Пройти ещё раз» начинает новую попытку с теми же правилами и выбранным режимом. Исходная история сохраняется.

Кнопка «Переиграть с этого решения» — следующее улучшение после готовности всех девяти требований. Она создаёт отдельную тренировочную попытку по сохранённому состоянию до ошибки. Нельзя переписывать старую проверку или начислять за возврат новые рейтинговые очки.

Разбор составляется из заранее подготовленных текстов в сценарии. Нейросеть для него не требуется. Движок выбирает объяснение по принятому действию и сохранённому правилу.

### Проверка готовности

Открыть правильную, ошибочную и просроченную попытки. Для каждой причины итогов понятны без рассказа разработчика. Последствия объясняются по той версии правил, по которой проходил игрок. Обращение к начальнику поезда не штрафуется само по себе: в выбранных исходных ситуациях оно предусмотрено. [2, № 16, 41]

# 8. Уведомления и временные баллы

## Требование 8. Уведомления

В сдаваемой версии реализовать **все три вида**, перечисленные в функциональных требованиях. В детализации оценивания встречается формулировка «или», но для этой реализации не используем её как повод убрать один из видов. [1, с. 2, 5]

| Вид | Что создаёт сообщение | Куда ведёт |
|---|---|---|
| Новый сценарий | Публикация версии, ещё не показанной этому профилю. | Карточка сценария. |
| Учебное испытание | Начало доступного испытания «Две ситуации — два решения». | Условие, прогресс, награда и срок. |
| Скоро сгорят баллы | До истечения временной награды остаётся не более часа. | Сведения о начислении и точное время сгорания. |

Уведомление хранит тип, заголовок, текст, связанный объект, время создания и отметку прочтения. Значок в верхней панели показывает количество непрочитанных. Открытие сообщения отмечает его прочитанным; обновление страницы не меняет эту отметку.

### Одно учебное испытание

Условие: зачесть оба сценария после начала испытания. Срок выполнения — 24 часа после присоединения. Награда — 20 временных баллов на 24 часа после выдачи. Эти числа служат для демонстрации механизма, а не взяты из требований перевозчика.

Игрок нажимает «Участвовать». Если уже есть старые зачёты, они не засчитываются автоматически: нужны попытки, завершённые после присоединения. Награда выдаётся один раз. Её срок и отличие от постоянных очков видны до участия.

Отдельный обработчик создаёт предупреждение за час до сгорания, а затем исключает просроченные баллы из суммы рейтинга. Каждое уведомление имеет ключ уникальности: профиль + событие + версия или награда. При повторной проверке дубликаты не появляются.

### Как показать за несколько минут

В локальном демонстрационном режиме создать временную награду с оставшимися 90 секундами и предупреждением за 60 секунд. На экране явно написать «Ускоренная демонстрация». Эти настройки отделены от обычных правил; посетитель публичной версии не может менять часы и выдавать себе баллы.

Проверить, что после сгорания меняется реальная запись награды и сумма рейтинга, а не только текст сообщения. Основные очки и уровень остаются прежними.

# 9. Аналитика прогресса

## Требование 9. Аналитика

Собирать действия на сервере, а не выводить заранее нарисованные проценты. Отдельно хранить навигационные действия, выбранные решения и системные события вроде просрочки. Не каждое нажатие является доказательством навыка.

### Три компетенции первой версии

| Компетенция | На чём основан вывод |
|---|---|
| Общение с пассажиром | Признание неудобства, понятные объяснения, отсутствие необоснованных обещаний и грубости. |
| Порядок действий | Проверка доступной альтернативы, передача информации нужным сотрудникам, возвращение к обращению. |
| Безопасность и приоритеты | Различение вещей с известным и неизвестным владельцем, освобождение прохода, своевременное информирование. |

Для первой смены есть девять пунктов оценки — по три на каждую компетенцию. Для второго сценария — четыре пункта, распределённые в его описании. Выводы относятся только к пройденным игровым ситуациям, а не ко всей профессиональной пригодности человека.

### Что видит игрок

Список попыток по дате; оценку и режим каждой; число выполненных пунктов по компетенции; самые частые ошибки; конкретную рекомендованную тренировку. До первых данных писать «Пока недостаточно наблюдений», а не ставить ноль как оценку способности.

Долю успешных действий считать только среди предусмотренных пунктов завершённых попыток. Обучение и проверка отображаются раздельно. Для общего обзора брать до пяти последних завершённых попыток каждого сценария; число наблюдений обязательно показывать рядом с долей. Сравнение во времени делать внутри одной версии сценария, иначе отмечать изменение условий.

### Правила рекомендаций

Ошибка приоритетов в первой смене — предложить обучение по первой смене и затем второй сценарий на различение обстоятельств. Не передано сообщение ответственным сотрудникам — повторить соответствующую ветку и показать основание. Необоснованное обещание — показать конкретную фразу из попытки и доступную альтернативу.

### Проверка готовности

Сделать две разные попытки. На экране появляются именно их данные, а не одинаковые образцы. Нажатие на ошибку открывает подтверждающее решение. Удаление демонстрационных начальных записей не уничтожает алгоритм аналитики. Приложение не объявляет улучшение реальных навыков доказанным по двум прохождениям.

# 10. Что можно взять из выбранной картинки

**Её можно использовать как образец оформления и источник небольших изображений. Нельзя просто вставить весь лист и считать, что готов интерфейс игры.**

Исходный файл имеет размер 1536 × 1024. В нём нет отдельных слоёв; весь альфа-канал непрозрачный. Светлые поля вокруг фигур — часть рисунка. Это проверено по переданному файлу, а не предположено по внешнему виду.

| Часть листа | Как использовать | Ограничение |
|---|---|---|
| Персонажи сверху | Небольшие карточки собеседников. | Фигуры обрезаны; это не полный рост для перемещения по вагону. |
| Ряды эмоций справа | Портреты в диалоге после проверки совпадения лица и одежды. | Между рисунками могут меняться черты; подпись «нейтральная» не гарантирует нейтральное выражение. |
| Салон снизу слева | Временное изображение сцены и образец для отдельного большого фона. | Фрагмент всего 402 × 246; при увеличении не появятся новые детали. |
| Предметы справа | Маленькие изображения в карточках предметов. | Светлый фон сохранён. Для свободного размещения нужна отдельная подготовка прозрачности. |
| Кнопки, шкалы, профиль | Повторить внешний вид средствами интерфейса. | Не использовать как картинки с неизменяемыми числами и надписями. |
| Знаки и логотип | Пока оставить в образце оформления. | Не считать сгенерированный знак официальным знаком перевозчика. |

### Что нельзя оставлять внутри игрового фона

Имя говорящего, реплики, выбранные ответы, проценты, время, баллы, сообщения и достижения. Всё это приходит из состояния игры и выводится обычным текстом и элементами интерфейса.

Багаж на верхних полках в рисунке является частью неподвижного фона. Его нельзя выбирать как отдельный предмет. Игровой чемодан появляется отдельной карточкой или отдельно подготовленным изображением. Не использовать уже нарисованную в фоне вещь для обещанной анимации перемещения.

Не менять выбранный полуреалистичный стиль на плоских векторных персонажей ради удобства. Сначала используем аккуратные карточки с вырезанными портретами; большие изображения готовим отдельно.

# 11. Как подготовить изображения: пошагово

### Шаг 1. Сохранить исходный лист

Файл `graphics/reference/board.png` — неизменённый источник. Он нужен дизайнеру и разработчикам, но не является главным экраном игры.

### Шаг 2. Вырезать изображения без подписей

В приложении к этому ТЗ уже подготовлены 30 фрагментов: 4 изображения помещений, 4 карточки персонажей, 10 портретов из рядов эмоций и 12 предметов. Они лежат в `graphics/crops/`. Это именно вырезанные фрагменты, не заново нарисованные объекты.

В `graphics/manifest.json` записаны размеры и исходные координаты каждого фрагмента. Светлый фон сохранён, прозрачности нет. Рисунки не увеличены искусственно. При повторной нарезке исходного файла те же координаты дают тот же результат.

| Файл | Координаты: слева, сверху, справа, снизу | Размер |
|---|---|---|
| `cabin_standard.png` | 11, 448, 413, 694 | 402 × 246 |
| `conductor_card.png` | 12, 110, 142, 349 | 130 × 239 |
| `passenger_card.png` | 146, 111, 277, 349 | 131 × 238 |
| `suitcase.png` | 978, 465, 1062, 554 | 84 × 89 |
| `socket.png` | 978, 592, 1062, 681 | 84 × 89 |

### Шаг 3. Использовать фрагменты там, где хватает размера

Портрет — около 80–110 пикселей по ширине, значок предмета — около 48–72. Это ориентир для первого экрана, а не запрет на другие размеры. Фон 402 × 246 подходит для небольшой иллюстрации; в крупной игровой сцене он будет мягким и должен быть заменён.

Светлую рамку портрета пока оставляем внутри светлой карточки. Не удалять все белые пиксели автоматически: белая рубашка и блики тоже могут исчезнуть. Не обещать прозрачность, пока она не проверена на тёмном и светлом фоне.

### Шаг 4. Заменить только крупные материалы

Заказать отдельно один фон стандартного салона не меньше 1920 × 1080, без людей, подписей, активного чемодана и выдуманных логотипов; три портрета не меньше 512 × 640; чемодан и розетку не меньше 512 × 512. Для предметов на сцене нужен прозрачный фон, для портретных карточек он необязателен.

Проверить, что лицо, причёска, одежда, ракурс и масштаб остаются одинаковыми между эмоциями. Не считать любое увеличенное изображение автоматически более качественным. Номер класса и расположение оборудования сверить с материалами заказчика, а не с подписью на сгенерированном листе.

# 12. Как собрать экран из этих частей

Картинка задаёт внешний вид. Сам экран делается из обычных элементов браузера: изображения, текст, кнопки, списки и полосы показателей. Браузерная разметка позволяет отдельно изменять текст и расположение. Для сохранения пропорций изображений использовать `object-fit`; обрезку портрета подбирать отдельно от размера его карточки. [4]

### Расположение на широком экране

Слева — компактная сцена вагона и список активных обращений. Справа — выбранный собеседник, его реплика и действия. Сверху — две шкалы и время текущего критического обращения. В нижней части — краткие сообщения о произошедших изменениях.

В первой версии персонажи и вещи могут оставаться в карточках поверх сцены. Не нужно дорисовывать ноги или маскировать непрозрачный прямоугольник под полноразмерного человека в проходе.

Игровой чемодан сначала находится в блоке «Проход». После подтверждённого сервером действия его карточка перемещается в блок «Багажная зона», а подпись меняется на «Проход свободен». Это условное изображение места, а не точная модель вагона.

### Порядок подключения

1. Подключить фон и карточки изображений, не добавляя внутрь них текст.
2. Сделать компоненты для диалога, действия, шкалы, срока и уведомления.
3. Передавать им данные из состояния попытки, полученного с сервера.
4. По нажатию отправлять идентификатор действия, а не новые баллы.
5. По ответу сервера обновлять сцену и показатели. При ошибке оставлять последнее подтверждённое состояние.
6. Состояние выражать не только цветом: добавлять подпись «Ожидает», «Решено», «Срок пропущен».

### Общие правила оформления

Основной текст — 16–18 пикселей; кнопки — не ниже 44 пикселей; вокруг содержимого карточки — 16–24 пикселя. Это параметры предлагаемого оформления, а не требования организаторов. Использовать системный шрифт с кириллицей, чтобы не зависеть от внешней загрузки.

На узком экране сцена становится небольшой иллюстрацией над диалогом. Кнопки идут одним столбцом; горизонтальной прокрутки нет. Проверить ширины 390, 768 и 1366 пикселей. Выбор доступен с клавиатуры, текущая кнопка выделяется, всплывающие сообщения не закрывают ответ.

В приложении есть `examples/screen-example.html`: пример размещения именно этих фрагментов. Он не обращается к серверу, не сохраняет результаты и не заменяет игру. Его назначение — показать, как картинки и работающие элементы интерфейса существуют отдельно.

# 13. Первая смена: неисправное оборудование

**Название:** «Сервис и свободный проход». Основа — ситуация № 16 «Не работает розетка/мультимедиа/кнопка вызова» и № 14 «Ручная кладь мешает проходу». [2, с. 7–8]

Источник по оборудованию предусматривает выслушать пассажира, извиниться, предложить пересадку при возможности и проинформировать начальника поезда и бортинженера. Самостоятельный ремонт проводником в этой игре не моделируется. [2, № 16]

### Исходные условия

Вымышленный пассажир сообщает: «Не получается зарядить ноутбук. Розетка у кресла не работает. Что можно сделать?» Пока это единственное обращение. Начальные шкалы — 60 и 80. Личность и номер места вымышлены.

Сценарий содержит заранее заданный признак доступности другого места. В основной демонстрации место есть; в дополнительном варианте его нет. Вариант фиксируется при старте и не меняется случайно посреди проверки. Игрок узнаёт его только после соответствующего действия.

### Шаги сервисного обращения

| Шаг | Выбор и результат |
|---|---|
| A0. Первое обращение | «Понимаю неудобство, давайте выясним, что можно предложить» — лояльность +5. «Сейчас обязательно починят» — +3 сейчас, но отметка необоснованного обещания. «Это не моя проблема» — −10. Все варианты ведут к A1. |
| A1. Проверка и сообщение | Можно проверить свободные места — перейти к A2. Можно сначала сообщить начальнику поезда и бортинженеру, остаться в A1 и затем проверить места. Повторное сообщение не приносит дополнительных очков. |
| A2. Альтернатива | При наличии места предложить пересесть: лояльность +10, далее A3. При отсутствии — честно объяснить, что свободного места нет: +5, далее A3. Вариант ответа зависит от проверенного условия. |
| A3. Завершение обращения | Если сообщение ответственным ещё не передано, передать его. После этого вернуться к пассажиру с подтверждённой информацией: лояльность +5, обращение закрыто. |
| Досрочное прекращение | «Закончить разговор без решения» — лояльность −10, обращение отмечено как незавершённое по существу. Второе обращение продолжает работать. |

После любого ответа в A0 открывается обращение о багаже и запускается его учебный срок. Переключение между обращениями свободное. Передача технической информации может быть как до проверки мест, так и после неё: это две допустимые последовательности.

Если в A0 было необоснованное обещание немедленного ремонта, при завершении сервисного обращения применить один раз лояльность −10 и показать, что обещание не подтверждено. Это придуманное авторами учебное последствие, а не цитата из регламента.

# 14. Первая смена: багаж и общий результат

После A0 появляется второе сообщение: «Чемодан мешает пройти». Срок 45 секунд начинается один раз, при открытии обращения B0. [2, № 14 — содержание ситуации; срок и баллы — настройки команды]

| Шаг | Выбор | Последствие |
|---|---|---|
| B0. Владелец неизвестен | Уточнить у пассажиров, кому принадлежит чемодан. | В этой учебной ситуации владелец отвечает. Устанавливается `owner_known = true`, переход B1. Шкалы без изменений. |
| B0. Отложить | «Сначала закончу другое обращение». | Лояльность −3 один раз. Шаг остаётся B0, срок не продлевается. |
| B1. Размещение | Вежливо объяснить причину и указать конкретное предусмотренное место. | Владелец размещает вещь. Безопасность +20, лояльность +10. Чемодан в багажной зоне, обращение закрыто. |
| B1. Грубое требование | Резко потребовать переставить вещь в указанное место. | Вещь убрана, безопасность +20, лояльность −15. Общение отмечено как ошибочное. |
| B1. Неясная просьба | Попросить убрать вещь, не указав куда. | Владелец уточняет место. Шаг остаётся B1, шкалы без изменений. Действие нельзя повторять бесконечно. |
| Срок истёк | Проход ещё занят. | Один раз безопасность −25, лояльность −5. Отметка просрочки. Игрок может закончить действие, но пропущенный срок не стирается. |

В этой сцене нельзя физически перемещать предмет до установления владельца. Источник требует найти владельца, вежливо попросить и указать конкретное место размещения. [2, № 14]

### Девять пунктов итоговой оценки

**Общение:** признал неудобство; не давал необоснованных обещаний; вежливо попросил освободить проход. **Порядок действий:** проверил доступность альтернативы; сообщил начальнику и бортинженеру; вернулся к пассажиру с результатом. **Безопасность:** установил владельца; указал предусмотренное место; освободил проход до срока.

Каждый пункт оценивается один раз. При досрочном завершении невыполненные пункты получают «не выполнено». Отсутствие свободного места само по себе не ошибка, если проверка выполнена и ограничение честно объяснено.

### Контрольные результаты

Полностью корректный маршрут при наличии места: лояльность 90, безопасность 100, выполнено 9 из 9, оценка 100. Та же последовательность с пропуском срока по багажу: лояльность 85, безопасность 75, 8 из 9, оценка 89; зачёта нет из-за порога безопасности. Корректные действия, но грубое требование: лояльность 65, безопасность 100, 8 из 9, оценка 89; зачёт есть, но разбор указывает ошибку общения.

Смена заканчивается, когда оба обращения закрыты, либо игрок явно завершил её досрочно. Итог сервисного обращения и наличие просрочки сохраняются отдельно от суммы баллов.

# 15. Второй сценарий: бесхозная вещь

**Название:** «Похожая вещь — другое решение». Основа — ситуация № 41 «Пассажир сообщает о бесхозной вещи». В источнике указано не трогать вещь, сообщить начальнику поезда и сотрудникам ПТБ по поездной радиосвязи. [2, с. 16]

Здесь используется похожее изображение чемодана, но игроку сразу сообщают другой существенный факт: пассажир сообщает о бесхозной вещи. Нельзя заставлять его угадывать это по цвету или форме предмета.

### Состояние и переходы

Начальные шкалы — лояльность 60, безопасность 80. На предусмотренное информирование даётся 35 учебных секунд. Действия по общению и передаче информации можно выполнить в любом порядке. Полную операцию транспортной безопасности этот короткий сценарий не изображает.

| Действие | Изменение состояния и оценка |
|---|---|
| Не трогать предмет и попросить пассажиров не приближаться | Сохраняется факт предупредительного общения. Лояльность +5, безопасность +10. |
| Сообщить начальнику поезда и сотрудникам ПТБ по поездной радиосвязи | Сохраняется информирование обеих сторон. Безопасность +10. Срок считается выполненным и закрывается. |
| Переместить вещь в багажную зону | Критическая учебная ошибка, безопасность −60, завершение с разбором. Никаких выдуманных взрывов или последствий, отсутствующих в источнике. |
| Отложить сообщение | Лояльность −5 один раз, ситуация остаётся активной, время не продлевается. |
| Срок сообщения истёк | Безопасность −30, критическая учебная отметка о пропущенном информировании. Дальше доступен разбор и повтор. |

После корректного информирования игра предлагает выполнить предупредительное общение, если оно ещё не выполнено. После двух правильных действий сценарий заканчивается. Срок закрывается своевременным сообщением, а не переходом на другую вкладку или просмотром подсказки. Уже зафиксированная просрочка не отменяется.

### Четыре пункта оценки

Не трогал предмет; сообщил начальнику поезда; сообщил сотрудникам ПТБ; корректно предупредил пассажиров. Последний пункт относится к общению, два сообщения — к порядку действий, невмешательство — к безопасности. Критическая просрочка учитывается отдельно в условии зачёта.

Правильный результат: лояльность 65, безопасность 100, 4 из 4, оценка 100. Обратный порядок двух правильных действий даёт тот же результат. Перемещение вещи не может быть зачтено за счёт хорошего обслуживания в предыдущей смене.

**Что согласовать с экспертом:** допустимые последовательности общения и информирования, формулировки последствий и учебный срок. Указание источника «действовать согласно алгоритму» не заменять собственноручно сочинённым полным алгоритмом.

# 17. Как принять действие и не испортить результат

### Последовательность обработки

1. Проверить сессию и принадлежность попытки текущему профилю.
2. Найти запись по идентификатору запроса. При точном повторе вернуть прежний ответ.
3. Начать транзакцию и заблокировать строку попытки на время изменения.
4. Применить наступившие сроки, которые ещё не обработаны.
5. Проверить номер состояния и доступность выбранного действия.
6. Применить действие, переходы, изменения шкал и новые сроки.
7. Записать событие и увеличить номер состояния.
8. При завершении рассчитать итог, лучший результат, достижения и испытание.
9. Сохранить ответ для повторного запроса, завершить транзакцию и вернуть состояние.

Для Laravel транзакции и блокировка изменяемых записей предусмотрены стандартными средствами. Их назначение здесь — не дать двум запросам начислить одни и те же очки. [5]

Если срок изменил состояние, но запрошенное действие уже недоступно, сохранить факт просрочки и вернуть актуальное состояние с понятной ошибкой. Нельзя откатывать просрочку вместе с отклонённым действием.

Идентификатор запроса, контрольную сумму содержимого и точный ответ хранить в `processed_requests`. Пара «профиль + идентификатор запроса» уникальна. Идентификатор связывать с профилем, операцией и содержимым. Если тот же идентификатор пришёл с другим действием, вернуть ошибку, а не повторить несвязанный ответ. Сначала проверять повтор, затем номер состояния: точный сетевой повтор после успешного ответа не должен ошибочно считаться новым устаревшим действием.

### Защита демонстрационной версии

Клиент не передаёт окончательные баллы, право на достижение или роль администратора. Разрешены только известные действия и перечисленные поля. Тексты показывать как текст, без исполнения разметки и программного кода из сценария.

Сессию хранить в защищённом cookie; изменение состояния защищать от посторонних запросов. Публикацию сценариев и ускоренную демонстрацию времени разрешать только локальной команде или отдельной административной роли. В публичном просмотре эти возможности недоступны.

В репозитории хранить пример настроек без настоящих ключей. Перед сдачей проверить историю Git, конфигурации, снимки экрана и данные. Не отправлять реальные документы пассажиров или сотрудников во внешние сервисы. Эти меры реализуют требования демонстрационной среды, но не означают проведённую промышленную или юридическую сертификацию. [1, с. 2, 5]

# 18. Программный интерфейс

Ниже предложен договор между интерфейсом и сервером. Он должен стать реальной документацией с примерами и ошибками. Наличие API для взаимодействия с кадровыми и учебными системами предусмотрено заданием. [1, с. 2–3, 5]

| `POST /api/v1/attempts/{id}/actions` | Отправить решение. |
| `POST /api/v1/attempts/{id}/pause` | Поставить обучение на паузу или снять паузу. |
| `POST /api/v1/attempts/{id}/finish` | Завершить попытку досрочно с подтверждением. |
| `GET /api/v1/attempts/{id}/result` | Получить результат и разбор завершённой попытки. |
| `GET /api/v1/me/progress` | Получить аналитику и рекомендации. |

| `PATCH /api/v1/notifications/{id}` | Отметить сообщение прочитанным. |
| `GET /api/v1/challenges` | Условия и состояние учебных испытаний. |
| `POST /api/v1/challenges/{id}/join` | Присоединиться к испытанию. |
| `GET /api/v1/integrations/results` | Отдать сохранённые результаты разрешённому внешнему клиенту. |

### Пример выбранного действия

```json
{
  "request_id": "a7f3d2e1-94b7-4e71-8e31-53f2b6d78a01",
  "expected_revision": 4,
  "thread_id": "baggage",
  "action_id": "identify_owner"
}
```

Ответ содержит подтверждённую ревизию, состояние обращений, шкалы, серверное время, сроки и доступные действия. Ошибки: 401 — нет сессии; 403 — нет прав; 404 — объект не найден; 409 — состояние изменилось или действие недоступно; 422 — неверные данные; 429 — слишком частые запросы. Понятное объяснение показывается игроку, технические подробности остаются в серверном журнале.

Для внешнего чтения выдавать отдельный ограниченный ключ, хранить его контрольное представление, не открывать все профили публично. Экспорт: вымышленный внешний идентификатор, версия сценария, режим, оценка, зачёт, компетенции, время завершения. Добавить постраничную выдачу. Это точка подключения, а не уже выполненная интеграция с реальной системой заказчика.

# 20. Порядок работы: от пустого проекта до смены

Работу делим на три направления: сервер и данные; интерфейс и изображения; сценарии, проверки и документы. Один человек может вести два направления. Отдельного сотрудника только ради этой схемы не требуется.

| Шаг | Что сделать | Готово, когда |
|---|---|---|
| 1. Зафиксировать договорённости | Принять девять требований, два сценария, режимы и формулу. Отправить эксперту спорные вопросы. Создать список задач и репозиторий. | У команды одинаковое понимание результата; неподтверждённые правила помечены. |
| 2. Поднять основу | Создать сервер, интерфейс, базу и локальный запуск. Настроить реальные коммиты по завершённым изменениям. | Другой участник открывает пустое приложение по инструкции. |
| 3. Профиль и сессия | Создать синтетический профиль и связь с браузером. | Обновление не теряет профиль, чужая попытка недоступна. |
| 4. Минимальный движок | Один узел, два действия, состояние, событие и итог. Пока без графики. | Два выбора дают два сохранённых результата через настоящий сервер. |
| 5. Условия и обращения | Разделить сервис и багаж, подключить признаки, переходы и доступность действий. | Переключение не сбрасывает другое обращение, недоступный выбор отвергается. |
| 6. Время и шкалы | Обработчик сроков, две шкалы, просрочка, защита от повторного действия. | Бездействие даёт последствие; двойной запрос не удваивает баллы. |
| 7. Первая смена целиком | Перенести разделы 13–14 в данные, добавить тексты разбора и контрольные результаты. | Оба корректных порядка дают ожидаемый итог; просроченный маршрут отличается. |

### Что делать параллельно

Пока пишется движок, подготовить карточки из выбранной картинки, общий вид панели и образцы текстов. Использовать временные данные только с явной отметкой. Как только готов запрос состояния, заменить временные значения реальными. Не держать две независимые системы подсчёта — в браузере и на сервере.

Не начинать с длинной регистрации, красивого стартового ролика или полного каталога персонажей. Первый важный результат — законченная попытка, которую можно открыть снова и объяснить.

После каждого шага сохранять работающий результат отдельным осмысленным изменением в Git. Не создавать фиктивную историю задним числом и не принимать большой непонятный фрагмент программы только потому, что он запускается.
